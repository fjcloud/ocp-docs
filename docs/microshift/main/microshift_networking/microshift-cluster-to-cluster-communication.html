Cluster-to-cluster communication

Cluster-to-cluster communication (C2CC) enables direct pod-to-pod and pod-to-service communication between independent MicroShift clusters on the same network segment or reachable through routable next-hops.

C2CC is built into MicroShift and is enabled entirely by the MicroShift configuration file. There is no separate service to install. Adding entries to the clusterToCluster.remoteClusters parameter enables the feature; removing the entries disables it and cleans up all C2CC-owned state.

Cluster-to-cluster communication (C2CC) for MicroShift is a Technology Preview feature only. Technology Preview features are not supported with Red Hat production service level agreements (SLAs) and might not be functionally complete. Red Hat does not recommend using them in production. These features provide early access to upcoming product features, enabling customers to test functionality and provide feedback during the development process.

For more information about the support scope of Red Hat Technology Preview features, see Technology Preview Features Support Scope.

C2CC provides the following capabilities:

  • Pod-to-pod communication across clusters by using pod IP addresses.

  • Pod-to-service communication across clusters (ClusterIP and headless Services) by using DNS names such as myservice.mynamespace.svc.cluster-b.remote.

  • Source pod IP preservation cross-cluster traffic bypasses source network address translation (SNAT), so NetworkPolicies on the remote cluster can enforce access control based on the originating pod IP.

  • Health monitoring per-remote-cluster health and latency reporting through the RemoteCluster custom resource.

  • IPv4, IPv6, and dual-stack support.

Cross-cluster traffic travels as plain routed IP over the underlay network. There is no tunnel between the hosts and no encryption by default. For production deployments, encrypting and authenticating this traffic with IPsec is strongly recommended.

Use C2CC when you deploy distributed solutions across multiple single-node MicroShift instances that need to consume each other’s workloads without a third-party interconnect solution.

Architecture of multi-cluster networking

When C2CC is enabled, the C2CC controller inside MicroShift automatically manages routing, network address translation (NAT), DNS forwarding, and health monitoring on each host.

Traffic flow

In a two-cluster setup, a pod on Cluster A reaches a pod or service on Cluster B in the following sequence:

  1. The pod sends traffic to the remote pod or service IP address.

  2. OVN-Kubernetes routes the packet to the OVN gateway router.

  3. A static route on the gateway router forwards traffic destined for remote pod and service classless inter-domain routings (CIDRs) to the configured next-hop (the remote cluster node IP) instead of the default gateway.

  4. The host forwards the packet over the underlay network as plain IP.

  5. The remote host receives the packet and routes it into the local OVN network.

Cross-cluster DNS queries follow a similar path. When a remote cluster has a domain configured, CoreDNS rewrites queries for that domain and forwards them to the remote cluster’s DNS service. Services on the remote cluster are resolvable as <_service_>.<_namespace_>.svc.<_domain_>.

Components managed by the C2CC controller

The C2CC controller reconciles continuously (event-driven, with a periodic fallback every few seconds). If routes, rules, or annotations are removed, for example by an OVN-Kubernetes restart, a firewall reload, or a host reboot, the removed items are restored automatically within seconds.

The controller manages the following subsystems:

OVN static routes

Routes on the OVN gateway router, such as GR_<_node_>, send traffic destined for remote pod and service classless inter-domain routings (CIDRs) to the configured next-hop. C2CC-owned routes are tagged with external_ids:k8s.ovn.org/owner-controller=microshift-c2cc.

Source network address translation (SNAT) bypass

nftables rules (commented c2cc-no-masq) in the OVN-Kubernetes ovn-kube-pod-subnet-masq chain and the node annotation k8s.ovn.org/node-ingress-snat-exclude-subnets prevent masquerading of cross-cluster traffic, which preserves original pod source IPs end-to-end.

Linux policy routing

Routes to remote CIDRs live in a dedicated routing table (default 200). A second table (default 201) reroutes inbound remote-to-local-service traffic through the OVN management port so that service load balancing does not SNAT the source.

Health probes

A lightweight c2cc-probe Deployment in the openshift-c2cc namespace probes each remote cluster’s probe Service through the full C2CC data path and reports the results in RemoteCluster custom resources.

Full-mesh topology

C2CC uses a static, full-mesh configuration. Each cluster lists every other cluster in its remoteClusters configuration. For N clusters, each host requires N-1 remote cluster entries.

C2CC requires bidirectional configuration. As a result, both clusters must configure each other as remotes. One-way setups are not supported.

Configure cluster-to-cluster communication

Configure cluster-to-cluster communication (C2CC) by setting non-overlapping pod and service classless inter-domain routing (CIDRs) on each cluster, adding remote cluster entries to the MicroShift configuration, configuring the firewall, and starting MicroShift.

MicroShift validates the C2CC configuration on startup. If validation fails because of overlapping CIDRs, a routing loop, or an invalid next-hop, MicroShift logs the errors and does not start. You must restart MicroShift for C2CC configuration changes to take effect.

MicroShift intentionally does not manage firewall rules because edge deployments often have site-specific firewall policies.

Prerequisites

  • Two or more hosts with MicroShift installed and the default OVN-Kubernetes CNI. C2CC requires OVN-Kubernetes and is not available with network.cniPlugin: none. Ideally, MicroShift has not been started yet so that cluster and service CIDRs can be set before the first boot.

  • IP connectivity between the hosts on the underlay network, for example, the same L2 segment or routable next-hops.

  • Non-overlapping pod and service CIDRs across all clusters. MicroShift defaults are 10.42.0.0/16 for pods and 10.43.0.0/16 for services, so all clusters except one must override them.

  • You installed the Red Hat build of MicroShift CLI (oc).

  • You have sudo privileges to each MicroShift host.

If MicroShift has already run, changing the network.clusterNetwork or network.serviceNetwork parameters requires wiping MicroShift data with the microshift-cleanup-data --all command, which deletes all workloads. Plan CIDRs before the first boot whenever possible.
Procedure

  1. On all clusters except one, override the pod and service networks before MicroShift starts for the first time.

    On Host B, add the following parameters to /etc/microshift/config.yaml or create a configuration snippet such as the following /etc/microshift/config.d/10-network.yaml:

    network:
  clusterNetwork:
  - 10.45.0.0/16
  serviceNetwork:
  - 10.46.0.0/16

    Host A can use the MicroShift defaults (10.42.0.0/16 and 10.43.0.0/16).

  2. On each host, create a configuration snippet that points at the remote cluster.

    1. On Host A, create /etc/microshift/config.d/50-c2cc.yaml by using the following parameters:

      clusterToCluster:
  remoteClusters:
  - nextHop:
    - 192.168.1.20
    clusterNetwork:
    - 10.45.0.0/16
    serviceNetwork:
    - 10.46.0.0/16
    domain: cluster-b.remote

    2. On Host B, create the same file describing Host A by using the following parameters:

      clusterToCluster:
  remoteClusters:
  - nextHop:
    - 192.168.1.10
    clusterNetwork:
    - 10.42.0.0/16
    serviceNetwork:
    - 10.43.0.0/16
    domain: cluster-a.remote

      For each remote cluster entry:

      • nextHop specifies the IP addresses of the remote cluster node used as the routing next-hop. Specify at most one IPv4 and one IPv6 address. Dual-stack clusters require both.

      • clusterNetwork and serviceNetwork specify the remote cluster pod and service CIDRs. These CIDRs must not overlap with the local networks or with any other remote.

      • domain sets an optional DNS suffix for the remote cluster. When set, services on the remote cluster are resolvable as <_svc_>.<_ns_>.svc.<_domain_>. When empty, no DNS forwarding is configured for this remote.

        To connect more than two clusters, add one remoteClusters entry per remote on every host.

  3. On each host, add the remote cluster pod and service CIDRs to the firewall trusted zone by using the following steps.

    1. On Host A, trust Host B’s pod and service CIDRs by running the following commands:

      $ sudo firewall-cmd --permanent --zone=trusted --add-source=10.45.0.0/16
$ sudo firewall-cmd --permanent --zone=trusted --add-source=10.46.0.0/16
$ sudo firewall-cmd --reload

    2. On Host B, trust Host A’s pod and service CIDRs by running the following commands:

      $ sudo firewall-cmd --permanent --zone=trusted --add-source=10.42.0.0/16
$ sudo firewall-cmd --permanent --zone=trusted --add-source=10.43.0.0/16
$ sudo firewall-cmd --reload

      Do not add the remote host’s own IP address to the trusted zone. C2CC is designed for pod-to-pod and pod-to-service traffic only. An untrusted host IP blocks host-originated traffic from reaching local pods.

  4. Start MicroShift by running the following command:

    $ sudo systemctl start microshift

    If MicroShift was already running and you changed network.clusterNetwork or network.serviceNetwork, wipe its data first with the microshift-cleanup-data --all command and then start the service.
Verification

  1. Verify that C2CC is active by running the following command:

    $ journalctl -u microshift --case-sensitive=false --grep c2cc
    Expected output
    C2CC is enabled with 1 remote cluster(s)

  2. Check the health of each remote cluster by running the following command:

    $ oc get remoteclusters.microshift.io
    Expected output
    NAME                AGE
c2cc-192-168-1-20   5m

    Each remote gets a cluster-scoped RemoteCluster resource named after its next-hop IP. The status.state field transitions from NeverProbed to Healthy when end-to-end probes succeed.

  3. Confirm that the remote cluster reports a healthy state by running the following command:

    $ oc get remoteclusters.microshift.io c2cc-192-168-1-20 -o jsonpath='{.status.state}{"\n"}'
    Expected output
    Healthy

  4. Inspect the routes that C2CC manages on Host A by running the following command:

    $ ip route show table 200
    Expected output
    10.45.0.0/16 via 192.168.1.20 dev enp1s0 proto 200
10.46.0.0/16 via 192.168.1.20 dev enp1s0 proto 200

    The following items indicate a successful configuration:

    • The journal shows C2CC is enabled with <_n_> remote cluster(s).

    • Each RemoteCluster resource reports status.state: Healthy.

    • Routes to remote CIDRs appear in the configured routing table. The default table ID is 200.

C2CC configuration examples

Use the following examples when you configure dual-stack C2CC clusters or disable cluster-to-cluster communication.

IPv6 and dual-stack example

C2CC supports IPv6-only and dual-stack clusters. The local and remote clusters must have compatible IP families. For every remote classless inter-domain routing (CIDR) family there must be a matching-family nextHop entry.

Dual-stack remote cluster configuration
clusterToCluster:
  remoteClusters:
  - nextHop:
    - 192.168.1.20
    - 2001:db8:0:1::20
    clusterNetwork:
    - 10.45.0.0/16
    - fd01:0:0:1::/64
    serviceNetwork:
    - 10.46.0.0/16
    - fd02:0:0:1::/112
    domain: cluster-b.remote

clusterNetwork and serviceNetwork must have the same number of entries with matching IP families at each position (at most one IPv4 and one IPv6 CIDR each).

Disable C2CC

Remove the C2CC configuration snippet (or the remoteClusters entries) and restart MicroShift by running the following command:

$ sudo rm /etc/microshift/config.d/50-c2cc.yaml
$ sudo systemctl restart microshift

On startup, the controller detects that C2CC is disabled and cleans up all C2CC-owned state: OVN static routes, kernel routes and rules, nftables rules, node annotations, the probe deployment, and the RemoteCluster resources.

Remember to remove the remote CIDRs from the firewall trusted zone as well.

If you overrode routing.routeTableID or routing.serviceRouteTableID, disable in two stages so the cleanup targets the right tables. First, remove only the remoteClusters entries while keeping the routing overrides and restart, and then remove the rest of the clusterToCluster section and restart again.

Deploy a service across multiple clusters

After you configure C2CC between clusters, you can deploy an application on one cluster and access it from a client pod on a different cluster by using cross-cluster DNS.

Use the two-cluster setup from the configuration procedure. Use the cluster-a.remote domain for Host A and use the cluster-b.remote domain for Host B.

Cluster-to-cluster communication (C2CC) for MicroShift is a Technology Preview feature only. Technology Preview features are not supported with Red Hat production service level agreements (SLAs) and might not be functionally complete. Red Hat does not recommend using them in production. These features provide early access to upcoming product features, enabling customers to test functionality and provide feedback during the development process.

For more information about the support scope of Red Hat Technology Preview features, see Technology Preview Features Support Scope.
Prerequisites

  • C2CC is configured and verified between the clusters. Each RemoteCluster resource reports status.state: Healthy.

  • You installed the oc CLI on each cluster.

  • You have access to both clusters.

Procedure

  1. On Host B, deploy a sample application and expose it as a Service by running the following commands:

    $ oc create namespace demo
$ oc -n demo create deployment hello --image=registry.access.redhat.com/ubi9/httpd-24
$ oc -n demo expose deployment hello --port=8080

  2. On Host A, deploy a client pod by running the following command:

    $ oc run curl-client --image=registry.access.redhat.com/ubi9/ubi-minimal --restart=Never -- sleep infinity

  3. From the client pod on Host A, resolve and reach the Service on Host B by using cross-cluster DNS:

    $ oc exec curl-client -- curl -s http://hello.demo.svc.cluster-b.remote:8080

    The DNS name format is <_service_>.<_namespace_>.svc.<_domain_>, where <_domain_> is the domain value configured for the remote cluster.

  4. Verify pod-to-pod connectivity by resolving a headless Service or using the remote pod IP directly by running the following command:

    $ oc exec curl-client -- curl -s http://<_remote-pod-ip_>:8080
Verification

  • The client pod on Host A successfully connects to the Service on Host B.

  • Cross-cluster DNS resolves hello.demo.svc.cluster-b.remote to the remote service IP.

    C2CC does not create NetworkPolicy resources. Namespaces with default-deny ingress must explicitly allow the remote pod classless inter-domain routings (CIDRs). ipBlock selectors work because original pod source IPs are preserved.

Encrypt C2CC traffic with IPsec

C2CC routes cross-cluster pod and service traffic as raw IP between nodes. This traffic traverses the physical network unencrypted by default. You can use IPsec to protect it using standard Linux tools on the host operating system.

MicroShift does not configure or manage IPsec. You must set up and maintain the IPsec tunnels.

Prerequisites

  • Two or more RHEL hosts running MicroShift with C2CC configured (non-overlapping pod and service classless inter-domain routings (CIDRs), clusterToCluster.remoteClusters populated in each node configuration).

  • IP connectivity between the hosts on the underlay network.

Procedure

  1. Install libreswan by running the following command:

    $ sudo dnf install -y libreswan

  2. Open the firewall for IKE negotiation and ESP on each host by running the following commands:

    $ sudo firewall-cmd --permanent --zone=public --add-service=ipsec
$ sudo firewall-cmd --reload

    UDP ports 500 and 4500 are for Internet Key Exchange (IKE), Network Address Translation Traversal (NAT-T)), and IP protocol 50 (Encapsulating Security Payload (ESP).

  3. Generate a pre-shared key on one host and distribute it to all others through a secure channel by running the following command:

    $ openssl rand -hex 32

  4. On Host A, create /etc/ipsec.d/c2cc.secrets with entries for every remote host by entering the following information:

    192.168.1.10 192.168.1.20 : PSK "<_your-hex-key_>"

  5. Set permissions for Host A by running the following commands:

    $ sudo chmod 600 /etc/ipsec.d/c2cc.secrets
$ sudo restorecon -v /etc/ipsec.d/c2cc.secrets

  6. On Host B, create /etc/ipsec.d/c2cc.secrets with entries for every remote host by entering the following information:

    192.168.1.20 192.168.1.10 : PSK "<_your-hex-key_>"

  7. Set permissions for Host B by running the following commands:

    $ sudo chmod 600 /etc/ipsec.d/c2cc.secrets
$ sudo restorecon -v /etc/ipsec.d/c2cc.secrets

  8. On Host A, create the /etc/ipsec.d/c2cc-tunnel.conf file by entering the following parameters:

    conn c2cc-to-host-b
    type=tunnel
    authby=secret
    left=192.168.1.10
    right=192.168.1.20
    leftsubnets={10.42.0.0/16 10.43.0.0/16}
    rightsubnets={10.45.0.0/16 10.46.0.0/16}
    auto=start
    ike=aes256-sha2_256-modp2048
    esp=aes256-sha2_256
    failureshunt=drop
    negotiationshunt=drop
    ikev2=insist

  9. On Host B, create the /etc/ipsec.d/c2cc-tunnel.conf file by entering the following parameters:

    conn c2cc-to-host-a
    type=tunnel
    authby=secret
    left=192.168.1.20
    right=192.168.1.10
    leftsubnets={10.45.0.0/16 10.46.0.0/16}
    rightsubnets={10.42.0.0/16 10.43.0.0/16}
    auto=start
    ike=aes256-sha2_256-modp2048
    esp=aes256-sha2_256
    failureshunt=drop
    negotiationshunt=drop
    ikev2=insist

    • The type=tunnel parameter encrypts the original IP packet and wraps it in a new IP header. This parameter is required because C2CC traffic uses pod and service CIDRs as source and destination, which are not routable on the underlay.

    • The values for the leftsubnets and rightsubnets parameters must match the pod and service CIDRs configured in MicroShift.

    • The failureshunt=drop and negotiationshunt=drop parameters drop traffic that matches the tunnel selectors if the security association (SA) fails or is still negotiating, preventing fallback to plain text.

  10. Initialize the NSS database only once and start the IPsec service by running the following commands:

    $ sudo ipsec checknss
$ sudo systemctl enable --now ipsec

  11. Verify that tunnel SAs are established by running the following commands:

    $ sudo ipsec trafficstatus
#8: "c2cc-to-host-b/1x1", type=ESP, add_time=..., inBytes=..., outBytes=..., id='192.168.1.20'
    Verification

    • ipsec trafficstatus displays type=ESP entries for each remote host.

    • Cross-cluster connectivity continues to work through the encrypted tunnels.

    • Byte counters in ip -s xfrm state increase while cross-cluster traffic is running.

      IPsec increases processing usage. ESP tunnel mode adds roughly 73–93 bytes per packet. On jumbo-frame networks with physical maximum transmission unit (MTU) 9000, set the pod MTU to leave headroom for ESP processing by creating /etc/microshift/ovn.yaml with mtu: 8900. Changing the pod MTU requires a node reboot to take effect.

Technology Preview features are not supported with Red Hat production service level agreements (SLAs) and might not be functionally complete. Red Hat does not recommend using them in production. For more information about the support scope of Red Hat Technology Preview features, see Technology Preview Features Support Scope.

Limitations

No authentication or encryption by default

Any host that can reach, or spoof, the configured next-hop IP can inject traffic into the cluster. Because source network address translation (SNAT) is bypassed, that traffic can carry an attacker-chosen source IP that matches NetworkPolicy allow rules.

Non-overlapping CIDRs required

Pod and service classless inter-domain routings (CIDRs) must not overlap across clusters. C2CC does not handle overlapping CIDRs. Plan unique CIDRs for each cluster before the first boot.

Static full-mesh configuration

Each cluster lists every other cluster in its configuration. This configuration does not scale to large fleets without external configuration automation. C2CC is validated with up to three interconnected clusters.

Restart required for changes

The C2CC configuration is read at startup. Any change such as adding or removing remotes, DNS TTLs, or routing tables requires a MicroShift restart.

NetworkPolicies are your responsibility

C2CC does not create NetworkPolicy resources. Namespaces with default-deny ingress must explicitly allow the remote pod CIDRs.

No MTU adjustment by C2CC

Cross-cluster traffic leaves the host as plain IP at the pod maximum transmission unit (MTU). On jumbo-frame networks, set the pod MTU explicitly in /etc/microshift/ovn.yaml. When using IPsec, leave space for ESP processing.

Validation failures block startup

Invalid C2CC configuration (overlapping CIDRs, routing loops, bad masks, duplicate next-hops or domains) prevents MicroShift from starting. Check journalctl -u microshift for the specific error.

Support exception for production use

Customers who require C2CC in production before it reaches general availability can request a support exception through the standard Red Hat support exception process. A support exception enables upgrades to a later general availability version without reinstallation.

Troubleshoot cluster-to-cluster communication

Use the following guidance to diagnose common C2CC issues related to overlapping CIDRs, connectivity failures, and configuration errors.

MicroShift fails to start after enabling C2CC

MicroShift validates the C2CC configuration on startup. Invalid configuration prevents the service from starting.

Check the journal for C2CC validation errors by entering the following command:

$ journalctl -u microshift --case-sensitive=false --grep c2cc

Common validation failures:

  • Overlapping CIDRs: pod or service CIDRs overlap between the local cluster and a remote cluster, or between two remote clusters. Each cluster must use unique pod and service CIDRs. If MicroShift has already started with default CIDRs, wipe data with microshift-cleanup-data --all and reconfigure before restarting.

  • Routing loop: a remote cluster’s CIDRs match the local cluster’s CIDRs.

  • Invalid next-hop: the next-hop IP equals the local node IP or is duplicated across remotes.

  • Invalid domain: the domain value is not a valid DNS subdomain, duplicates another remote, or equals cluster.local.

RemoteCluster reports unhealthy status

Check the RemoteCluster resource for error details by entering the following command:

$ oc get remoteclusters.microshift.io -o yaml

Verify that routes to remote CIDRs exist by entering the following command:

$ ip route show table 200

Verify that the firewall allows traffic from remote pod and service CIDRs by entering the following command:

$ sudo firewall-cmd --zone=trusted --list-sources

Ensure remote CIDRs are in the trusted zone, not the remote host IP.

Verify underlay connectivity between the hosts by entering the following command:

$ ping <_remote-host-ip_>

Inspect SNAT bypass rules by entering the following commands:

$ sudo nft list chain inet ovn-kubernetes ovn-kube-pod-subnet-masq
$ oc get node -o jsonpath='{.items[0].metadata.annotations.k8s\.ovn\.org/node-ingress-snat-exclude-subnets}'

Cross-cluster DNS resolution fails

Verify that the remote cluster has a domain configured in the clusterToCluster.remoteClusters parameter by entering the following command:

$ sudo microshift show-config --mode effective

Confirm that each remote cluster entry that needs cross-cluster DNS has a non-empty domain value.

Inspect the CoreDNS Corefile for the remote domain forwarding block by running the following command:

$ oc get configmap -n openshift-dns dns-default -o jsonpath='{.data.Corefile}'

Test DNS resolution from a client pod by entering the following command:

$ oc exec <_pod_> -- nslookup <_service_>.<_namespace_>.svc.<_domain_>

Pod-to-pod connectivity fails but DNS works

Verify that NetworkPolicies on the remote cluster allow traffic from the originating pod CIDR. C2CC preserves source pod IPs, so ipBlock selectors must include the remote cluster’s pod CIDR.

Use the remote pod IP directly to test connectivity by entering the following command:

$ oc exec <_pod_> -- curl -s http://<_remote-pod-ip_>:<_port_>

Stale routes after changing routing table IDs

MicroShift does not clean up C2CC routes on shutdown. If you change the routing.routeTableID or routing.serviceRouteTableID parameters while C2CC is enabled, routes and rules in the old tables remain until a reboot or manual cleanup. To change the routing.routeTableID or routing.serviceRouteTableID parameters, run the following commands:

$ sudo ip route flush table <_old-table-id_>
$ sudo ip rule del to <_remote-cidr_> lookup <_old-table-id_>

Overlapping CIDRs

C2CC requires non-overlapping pod and service CIDRs across all clusters. If multiple clusters use the default CIDRs (10.42.0.0/16 and 10.43.0.0/16), only one cluster can keep the defaults.

To resolve overlapping CIDRs, perform the following actions:

  • Plan unique CIDRs for each cluster before the first boot.

  • On clusters that need non-default CIDRs, set network.clusterNetwork and network.serviceNetwork before starting MicroShift.

  • If MicroShift has already run with overlapping CIDRs, wipe data on affected clusters with microshift-cleanup-data --all, reconfigure with unique CIDRs, and restart.

Changing network.clusterNetwork or network.serviceNetwork on a cluster that has already started requires wiping MicroShift data, which deletes all workloads.

Table 2. C2CC configuration fields definitions table
Parameter Description

clusterToCluster

The clusterToCluster section of the MicroShift configuration file defines the configurable parameters for cluster-to-cluster communication. All of the following parameters in this table are subsections in the clusterToCluster section of the MicroShift configuration. C2CC is disabled when remoteClusters is empty.

remoteClusters

Is a subgroup that lists the remote clusters. Add one entry per remote cluster on every host in a full-mesh topology.

remoteClusters.nextHop

Specifies the next-hop IP addresses of the remote node. At most one IPv4 and one IPv6 address are allowed. The addresses must not equal the local node IP or duplicate another remote. This field is required.

remoteClusters.clusterNetwork

Specifies the remote pod classless inter-domain routings (CIDRs). The CIDRs must not overlap with local or other remote CIDRs. The minimum mask is /8 for IPv4 or /32 for IPv6. This field is required.

remoteClusters.serviceNetwork

Specifies the remote service CIDRs. The same constraints apply as for clusterNetwork. The list must have the same number of entries with matching IP families. This field is required.

remoteClusters.domain

Specifies an optional DNS suffix for the remote cluster. The value must be a valid DNS subdomain, unique across remotes, and not cluster.local. When set, Services on the remote cluster are resolvable as <_svc_>.<_ns_>.svc.<_domain_>. When unspecified, domain defaults to "". There is no DNS forwarding for this remote. NOTE: The remoteClusters.domain parameter only works with the Corefile generated by Red Hat build of MicroShift and is not applicable if you use the bring-your-own Corefile feature.

probeInterval

Specifies the interval between health probes to each remote cluster. The value is a Go duration string between 1s and 5m. When unspecified, probeInterval defaults to 10s.

dns

dns is a subgroup that specifies DNS cache settings for remote domains.

dns.cacheTTL

Specifies the maximum TTL in seconds for positive DNS cache entries for remote domains. A value of 0 disables caching. When unspecified, cacheTTL defaults to 10.

dns.cacheNegativeTTL

Specifies the maximum TTL in seconds for negative (NXDOMAIN or NODATA) DNS cache entries. A value of 0 disables caching. When unspecified, cacheNegativeTTL defaults to 10.

routing

routing is a subgroup that specifies Linux policy routing table IDs for C2CC routes.

routing.routeTableID

Specifies the Linux policy routing table for routes to remote CIDRs. The range is 1–252 and the value must differ from serviceRouteTableID. When unspecified, routeTableID defaults to 200.

routing.serviceRouteTableID

Specifies the Linux policy routing table for service routes through the OVN management port. The range is 1–252 and the value must differ from routeTableID. When unspecified, serviceRouteTableID defaults to 201.

The routing table IDs only need to be changed if other software on the host, for example, NetworkManager dispatcher scripts or VPN tooling, already uses tables 200 and 201.
