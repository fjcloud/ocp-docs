Distributing certificates by using the trust-manager operand

  • The trust manager operand
  • The trust-manager operand
  • Configuring a trust bundle
  • Configuring the trust-manager operand
  • Trust-manager operand configuration attributes

The trust-manager operand simplifies the distribution of certificate authority (CA) certificates across {microshift-short} nodes. As an administrator, you can configure the operand according to the cluster requirements and manage trust bundles efficiently.

Technology Preview features are not supported with Red Hat production service level agreements (SLAs) and might not be functionally complete. Red Hat does not recommend using them in production. These features provide early access to upcoming product features, enabling customers to test functionality and provide feedback during the development process.

For more information about the support scope of Red Hat Technology Preview features, see Technology Preview Features Support Scope.

The trust-manager operand provides the following benefits:

  • Distribution of CA certificates across your nodes as a postinstallation operation.

  • Consolidation of certificates from multiple sources, such as ConfigMaps, Secrets, inline data, and default CAs, into a single trust bundle.

  • Automatic updates to target objects whenever the underlying source certificates change.

  • Creation of trust bundles as secret objects for applications that explicitly require secrets instead of ConfigMap objects.

  • Automatic integration with the default trusted CA bundle of the cluster, requiring no manual configuration.

The trust manager operand

In {microshift-short}, the trust-manager operand extends cert-manager to manage and distribute CA certificates across the node. You can use it to propagate custom CA certificates to target namespaces so edge applications can verify TLS connections to local host hardware endpoints.

Host physical devices often present local TLS-secured endpoints (for example, GPU services, custom serial interfaces, or local cryptographic modules) that use self-signed or enterprise-signed CA certificates. Instead of manual certificate copying, the trust-manager operand enables you to define a single Bundle custom resource.

This custom resource reads certificate data from a designated source namespace and replicates a synchronized ConfigMap containing the trust bundle to target namespaces that you select. When certificate data changes at the host level, the operand automatically updates the synchronized trust bundle in the target namespaces. This synchronization mechanism maintains uninterrupted and secure communications for edge workloads.

The trust-manager operand

You can install the trust-manager operand to enable the automated distribution of trust bundles across your node namespaces. The trust-manager operand is not installed by default.

Technology Preview features are not supported with Red Hat production service level agreements (SLAs) and might not be functionally complete. Red Hat does not recommend using them in production. These features provide early access to upcoming product features, enabling customers to test functionality and provide feedback during the development process.

For more information about the support scope of Red Hat Technology Preview features, see Technology Preview Features Support Scope.
Prerequisites

  • You have access to the cluster with cluster-admin privileges.

  • You have installed cert-manager Operator for Red Hat OpenShift.

Procedure

  1. Create a YAML file, for example, trust-manager.yaml, that defines the TrustManager custom resource (CR) as shown in the following example:

    Example trust-manager.yaml
    apiVersion: operator.openshift.io/v1alpha1
kind: TrustManager
metadata:
   name: cluster
spec:
   trustManagerConfig: {}

  2. Create the TrustManager CR by running the following command:

    $ oc create -f trust-manager.yaml
Verification

  1. Verify that the trust-manager operand is running successfully by running the following command:

    $ oc get TrustManager cluster -o jsonpath='{.status.conditions}' | jq
    Example output
    [
  {
    "lastTransitionTime": "2026-03-27T11:54:50Z",
    "message": "",
    "reason": "Ready",
    "status": "False",
    "type": "Degraded"
  },
  {
    "lastTransitionTime": "2026-03-27T11:54:50Z",
    "message": "reconciliation successful",
    "reason": "Ready",
    "status": "True",
    "type": "Ready"
  }
]

    The message field in the output must have the value reconciliation successful.

  2. Verify that the trust-manager deployment is running successfully in the cert-manager namespace by running the following command:

    $ oc get deployments -l "app.kubernetes.io/name=cert-manager-trust-manager" -n cert-manager
    Example output
    NAME            READY   UP-TO-DATE   AVAILABLE   AGE
trust-manager   1/1     1            1           109s

  3. Verify that the status of the pod is Running by running the following command:

    $ oc get pods -l "app.kubernetes.io/name=cert-manager-trust-manager" -n cert-manager
    Example output

trust-manager-547bb59b4b-hd6mv    1/1     Running   0          24s

Configuring a trust bundle

After installing the trust-manager operand, you must use the Bundle custom resource (CR) to distribute certificate authority (CA) certificates across your cluster. A trust bundle combines certificate sources and maintains target ConfigMap and Secret objects across selected namespaces.

If you want to manually configure the CA content, you must create a cert-manager-operator-trusted-ca-bundle config map in the cert-manager-operator namespace by running the following command:

$ oc create configmap cert-manager-operator-trusted-ca-bundle \
  -n cert-manager-operator \
  --from-file=ca-bundle.crt=/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem

Prerequisites

  • You have access to the cluster with cluster-admin privileges.

  • You have installed the trust-manager operand.

Procedure

  1. To inject the trust bundle into a specific namespace, apply the required label by running the following command:

    $ oc patch namespace <namespace> --type=merge -p '{"metadata":{"labels":{"trust.cert-manager.io/inject":"true"}}}'

    The trust-manager operand creates the target bundle in all namespaces that match the label selector defined in your Bundle CR.

  2. Create a YAML file, for example, bundle.yaml, that defines the Bundle object as shown in the following example. You must manually create a cert-manager-operator-trusted-ca-bundle config map to use the sources.useDefaultCAs parameter.

    Example YAML file that defines the Bundle object
    apiVersion: trust.cert-manager.io/v1alpha1
kind: Bundle
metadata:
  name: example-bundle
spec:
  sources:
    - useDefaultCAs: true
  target:
    configMap:
      key: ca-certificates.crt
    secret:
      key: ca-certificates.crt
    namespaceSelector:
      matchLabels:
        trust.cert-manager.io/inject: "true"

    If your Bundle CR targets a Secret object, you must set the spec.trustManagerConfig.secretTargets.policy field in your TrustManager CR to Custom and add the name of target secret to the spec.trustManagerConfig.secretTargets.authorizedSecrets list. If the spec.trustManagerConfig.secretTargets.policy field is set to Disabled, the Bundle CR fails to create the target secret.

  3. Create the Bundle custom resource by running the following command:

    $ oc create -f bundle.yaml
Verification

  1. Verify the status of Bundle CR by running the following command:

    $ oc get Bundle example-bundle -o jsonpath='{.status.conditions}' | jq

    In the output, the reason must be set to Synced and status must be set to True, as shown in the following example:

    Example output
    [
  {
    "lastTransitionTime": "2026-03-27T12:03:42Z",
    "message": "Successfully synced Bundle to namespaces that match this label selector: trust.cert-manager.io/inject=true",
    "observedGeneration": 1,
    "reason": "Synced",
    "status": "True",
    "type": "Synced"
  }
]

  2. Verify the target secret by running the following command:

    $ oc describe secret example-bundle -n trust-bundle-target
    Example output
    Name:         example-bundle
Namespace:    trust-bundle-target
Labels:       trust.cert-manager.io/bundle=example-bundle
Annotations:  trust.cert-manager.io/hash: 55c00f8109c4c6b1ee4710aa53ad280355973f25444d6bb13a93851af0d8f5d8

Type:  Opaque

Data

ca-certificates.crt:  219257 bytes

  3. Verify the target ConfigMap by running the following command:

    $ oc get cm example-bundle -n trust-bundle-target
    Example output
    NAME             DATA   AGE
example-bundle   1      4m25s

Configuring the trust-manager operand

To establish secure TLS connections between containerized applications and host hardware device endpoints, configure the trust-manager operand to distribute host CA certificates to your application namespaces.

Technology Preview features are not supported with Red Hat production service level agreements (SLAs) and might not be functionally complete. Red Hat does not recommend using them in production. These features provide early access to upcoming product features, enabling customers to test functionality and provide feedback during the development process.

For more information about the support scope of Red Hat Technology Preview features, see Technology Preview Features Support Scope.
Prerequisites

  • You have access to the cluster with cluster-admin privileges.

  • You have installed the cert-manager Operator and the trust-manager operand.

  • The custom CA certificate of the host hardware device is available as a ConfigMap named host-device-ca in the cert-manager namespace.

Procedure

  1. Define a Bundle custom resource that specifies the source certificate and the target namespaces. Create a file named host-device-bundle.yaml with the following content:

    apiVersion: trust.cert-manager.io/v1alpha1
kind: Bundle
metadata:
  name: host-device-trust
spec:
  sources:
    - configMap:
        name: host-device-ca
        key: ca.crt
  target:
    configMap:
      key: ca-bundle.crt

  2. Apply the Bundle custom resource manifest to your node by running the following command:

    $ oc apply -f host-device-bundle.yaml

  3. Edit your application Pod specification to mount the distributed trust bundle ConfigMap. Create a file named application-pod.yaml with the following content:

    apiVersion: v1
kind: Pod
metadata:
  name: host-device-app
  namespace: app-namespace
spec:
  containers:
    - name: device-connector
      image: ubi8/ubi:8.10
      volumeMounts:
        - name: trust-bundle
          mountPath: /etc/pki/ca-trust/extracted/pem
          readOnly: true
  volumes:
    - name: trust-bundle
      configMap:
        name: host-device-trust

  4. Create the Pod in your namespace by running the following command:

    $ oc apply -f application-pod.yaml
Verification

  1. Verify that the trust-manager operand successfully created and distributed the ConfigMap to your application namespace by running the following command:

    $ oc get configmap host-device-trust -n app-namespace
    Expected output:
    NAME                DATA   AGE
host-device-trust   1      2m

  2. Verify that the application container can read the mounted CA certificate file from the mount path by running the following command:

    $ oc exec host-device-app -n app-namespace -- ls /etc/pki/ca-trust/extracted/pem
    Expected output:
    ca-bundle.crt

Trust-manager operand configuration attributes

View the Attributes of the Bundle custom resource table to identify and understand the configuration attributes. These attributes specify how the operand retrieves and distributes certificate authority (CA) certificates.

Table 1. Attributes of the Bundle custom resource
Attribute Type Description

spec.sources

Array of objects

Specifies the list of sources from which the operand retrieves CA certificate data.

spec.sources.configMap

Object

Configures the operand to retrieve CA certificate data from a ConfigMap in the cert-manager namespace.

spec.sources.configMap.name

String

Defines the name of the source ConfigMap in the cert-manager namespace.

spec.sources.configMap.key

String

Specifies the key in the source ConfigMap that contains the PEM-encoded CA certificate data.

spec.sources.secret

Object

Configures the operand to retrieve CA certificate data from a Secret in the cert-manager namespace.

spec.sources.secret.name

String

Defines the name of the source Secret in the cert-manager namespace.

spec.sources.secret.key

String

Specifies the key in the source Secret that contains the PEM-encoded CA certificate data.

spec.target.configMap.key

String

Specifies the key in the target ConfigMap where the operand writes the synchronized PEM CA certificate bundle.
